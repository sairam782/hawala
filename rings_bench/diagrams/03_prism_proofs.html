Who looks at this, for what

The teammate running the PRISM side, to know which bench runs to send and which clicks to rehearse; a judge who asks "which of these is the Sessions proof". Read one row left to right: the proof, the runs, the calls, the clicks, the screen. The track is Money Operations (the team's call at 11:14); the organizers' demo line for it is "the failure, the fix, and the alert that would have caught it".

What each column is for

  • Which runs produce it: the bench already produces all three. Sessions is every v2 run (seven named steps), Alert is any family that returns no answer or runs slow, Root Cause is the scorer's failure tags (missed_ring:shape, false_ring) sent to PRISM.
  • What code sends: the exact route and credit price, so no proof is attempted without knowing its cost. Two of three proofs cost nothing.
  • What a person clicks: the organizers' wording asks for dashboard clicks on Root Cause (tick, Analyze selected, Analyze now); Sessions and Alert can be made by code and shown on screen.
  • The proof on screen: what to screenshot the moment it appears. The fired alert is the one that depends on live timing, so it is screenshotted first.

Assumed (dashed cells)

  • Proof 3: that a wrong answer with a success status is invisible to clustering. In the practice runs, analyzed traces clustered and plain error traces alone did not; the exact rule is unconfirmed, so the failed v1 runs are sent with an error status and analyzed.

Not drawn

Trust & Risk (guardrail in Block mode, block check, Root Cause on blocked runs): the earlier track, dropped at 11:14; one line under the table says what it would take. Money Intelligence (Knowledge Base, evaluator v1 vs v2, Root Cause): not required now; the evaluator stays an option in the technical page's credits note.
