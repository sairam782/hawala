## What Jev's numbers mean here

- A Choice returns a probability per option and a **confidence** number, which measures how concentrated the
  probabilities are and is "not the chance of being right" (style guide lines 28 to 29). For a two-option Choice the
  confidence is 2 x max probability minus 1 (TypeSafe's spread formula, `bench\jev.py` `spread_confidence`), so
  binning by confidence is binning p(ring) folded around 0.5.
- A Score returns a position on described levels; the kit's `position()` rescales it to 0 to 1. The task's "0 to 100"
  score is position x 100 from a five-level scale (lines 131 to 135: three to five levels, use the position, not the
  top level).

## The three state variants

| variant | what Jev reads | rule and source |
|---|---|---|
| `rows_facts` | the code facts (`facts.facts_text`) first, then the raw transfer rows | the task's main variant; facts put first because a fact at the start scores higher than in the middle or end (line 304) |
| `facts` | the code facts only | the task's second variant; irrelevant content shifts borderline answers (lines 295 to 301), so the rows are dropped |
| `sentences` | the facts rewritten as plain sentences with every comparison done by code (`jev_options\jev_common.py` `state_text`, built at 12:27) | added because "Label: value" number forms misread and code-made bands written as sentences reach the strongest answers (lines 315 to 346); inventory rule: this builder already existed |

Format itself is a minor choice (line 348), so no JSON variant was tried.

## The three questions (one call per state, all three questions in it; line 491: ask everything at once)

1. **scheme**, a Choice with two options, ring and ordinary.
   - One Choice rather than a yes/no (line 115: a forced choice is more decisive on ambiguous input).
   - Full option descriptions, not keywords (lines 104 to 109); plain and positive wording, edge cases in the
     criteria (lines 95 to 97): "a busy account is not by itself suspicious", "recurring payments ... are ordinary".
   - The question opens with "judging only from the transfers and the code-computed facts" so a literal witness can
     answer it (line 67, the clarity test).
   - No "can't tell" option (lines 219 to 227); don't-know is read from p(ring) in code.
2. **pattern**, one Choice over the bench's nine names: fan-out, fan-in, cycle, chain, scatter-gather, mesh, lone,
   other, none.
   - One Choice for categories that exclude each other (line 148), every legal option offered (line 139).
   - "other" names what it excludes (line 160: a catch-all must name its exclusions); "none" describes the input
     (ordinary traffic), never the reader's ignorance (line 219).
   - Option order kept as the bench's list; order does not matter on Jev (line 154).
   - Each description names the code fact that would show the shape ("the facts list a directed loop ..."), because
     Jev matches what is there (using-jev.md, point 1: "your descriptions steer it").
3. **evidence**, a Score with five described levels from "no structure at all" to "overwhelming".
   - Levels described concretely, three to five of them, read by position (lines 124 to 135).
   - Each level names code facts, not adjectives, because new level descriptions move scores by a median 0.22 of a
     level (line 129), so they were written once and kept fixed across all runs of a set.

## Rules about the state that were checked, not just followed

- Code does the counting; Jev judges (line 58). Every number Jev sees was computed by `facts.py`.
- Blank-input check (line 239): the smallest unit has 6 rows; none is blank.
- The subject is described (line 245): the state is the whole neighborhood, nothing about other neighborhoods.
- Timestamps (line 310): the rows carry them; the facts carry the span. Not relevant to the judgment asked.
- Pinned model version logged with every answer (line 487): `jev-1.13.0`, in every record of `out\calls_*.jsonl`.
- Hostile input (lines 438 to 467): not applicable; the states are generated by our code from IBM's synthetic rows.

## Rules about testing

- Held-out looked at once (line 476): question set 1 was tuned on nothing and read on main, then heldout_a. Question
  set 2 (rulings) was written from the main-slice errors and then read on heldout_b, which no Jev question had seen.
  heldout_a was also re-run with set 2 for the gate comparison, but it is not a clean held-out for set 2, since its
  set 1 results had been seen.
- Thresholds per action from the cost of being wrong (line 355): the gate threshold was chosen on main (best F1 of the
  gated Sonnet result) and applied unchanged to the held-out slices.
- A Choice's probability can serve as a risk score (line 389): p(ring) was swept as a gate signal beside the Score.
- Test-set size (line 470): 60 units per slice means any accuracy is uncertain by about plus or minus 12 points;
  a 20-ring count by about plus or minus 4.

## Question set 2: rulings written into the descriptions (line 383)

After reading the set 1 errors on main: 28 of 40 ordinary units have pass-through pairs in the code facts (money
arriving at an account and leaving within 48 hours), and set 1's ring description said that counts. The rulings,
one sentence each, both sides named (using-jev.md recipe 2: "state each boundary narrowly, with both sides named"):

- ring only when the facts show a loop, a burst to or from three or more different accounts within an hour, or
  pass-through pairs with similar amounts linking three or more accounts in a line;
- a pass-through pair on its own is ordinary, even many of them, when amounts do not match or they do not link into a
  line of three; a busy account without a burst is ordinary; recurring payments are ordinary.

The Score's levels were rewritten to the same vocabulary. The pattern question was left as it was.
